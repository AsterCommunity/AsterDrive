# Authentication budgets and trust boundaries

MFA uses writer-owned account budgets, independently of optional HTTP/IP limiting. Login and sensitive management have separate budgets: five failures in a fixed fifteen-minute window trigger a fifteen-minute cooldown. Replacing flows, sessions or sensitive actions does not refresh the matching budget. Denied requests do not extend cooldown; success resets only its purpose. Administrator MFA reset clears all budgets. Email resend has an independent persisted reservation, serialized with code replacement, and consuming a code or failing delivery does not reset cooldown. At most three budget rows exist per account.

Passkey challenges and internal signed-request nonces use database uniqueness and consumption CAS in `auth_once_states`. Database failure rejects the operation without an independently consumable cache fallback. Challenges are consumed before credential verification. Each write collects at most 128 expired rows through the expiry index; payloads are bounded to 256 KiB and keys to 1024 bytes. Upgrade both Primary and Follower; pre-upgrade Passkey flows that existed only in cache must restart. Ordinary content-cache fallback is unchanged.

Restricted password-change sessions cannot obtain authenticated custom configuration. Password changes recheck the verified password hash, signed account generation, current session revocation and expiry under writer locks. Email confirmation rechecks the current blocklist while retaining existing allowlist grandfathering. SSE retains the access token's absolute expiry and terminates at expiry. Authentication/API limiter counters are created outside the HTTP worker factory and shared within the process; MFA budgets remain active when HTTP limiting is disabled.

Explicit deployment HTTP/HTTPS choices remain supported for findings 6, 34 and 33. The application still owns body-digest verification, replay protection, destination scope and redirect behavior. Multipart cancellation validates the complete listing before reconstructing upload-specific deletion keys. Noncanonical target keys are rejected before reference guards. Buffered tunnel JSON is hashed before decoding/dispatch. Owner proxies do not follow redirects.

Generated POSIX enrollment commands quote arguments and use a quoted heredoc with `--token-stdin`, keeping tokens out of process argv. aria2 tests reuse a stored hidden secret only at the saved normalized endpoint; a changed endpoint requires an explicit draft secret. Follower translations use locally generated node/connector namespaces and bounded full-bundle replacement, never application-owned namespaces.

COS browser uploads use existing server relay because long-lived read/write PUT signatures cannot prohibit unsigned copy-source headers. Storage, downloads, native processing and server-side multipart remain supported. Azure client multipart write capability stays on a temporary key; completion copies to a fresh key and checks size before publishing metadata. Azure fallback scratch remains exclusively created with Unix mode 0600, and download SAS signs response-type/attachment restrictions.

Provider session initialization reserves a database upload row under the policy lock before external allocation. Failure compensates the reservation; installing the result requires a session CAS. OneDrive configuration-only tenant/cloud edits reconcile saved application identity and incompatible grants. Driver entries bind policy snapshots and credential generations; retired callers cannot replace the current cache, and credential publication shares synchronization with invalidation.

No dependency fork/vendor is introduced. Local protocol fixtures, real-provider IAM acceptance, TLS deployment and production rollout are separate evidence boundaries.

COS upload URLs issued before upgrade remain valid until their existing expiry; immediate revocation requires rotating their signing credentials. The new version stops issuing that browser write delegation.
